# 方案设计文档 v3.0 — 同质化案件文档检索与规则系统

> 版本: v3.0
> 日期: 2026-08-12
> 状态: 方案设计阶段，待确认后进入详细设计

---

## 1. 一句话说清这个系统是什么

**把法务部门的历史案件卷宗、审核经验、检查清单全部结构化存储，让文员在新案件到来时能快速检索历史参考、按清单逐项审核、持续积累经验。**

---

## 2. 核心概念

**三个核心对象，而不是一个：**

```
┌─────────────────────────────────────────────────────────┐
│                                                         │
│   案件（NocoDB）          文档（Paperless-ngx）           │
│   ┌──────────────┐       ┌──────────────┐               │
│   │ 案号          │       │ 判决书 PDF    │               │
│   │ 案由          │───→   │ 起诉状 PDF    │               │
│   │ 当事人        │       │ 证据清单 PDF   │               │
│   │ 侵权事实      │       │ 鉴定报告 PDF   │               │
│   │ 赔偿金额      │       │ ...           │               │
│   │ 审核结论      │       └──────────────┘               │
│   │ ...           │                                      │
│   └──────┬───────┘                                       │
│          │                                               │
│          │ 关联                                          │
│          ▼                                               │
│   规则/清单（NocoDB）                                     │
│   ┌──────────────┐                                       │
│   │ 权属审查清单   │  ← 适用案由：著作权纠纷               │
│   │ 侵权认定清单   │  ← 适用案由：著作权纠纷               │
│   │ 赔偿标准参考   │  ← 适用案由：全部                     │
│   │ 证据审查清单   │  ← 适用案由：商标纠纷                 │
│   │ ...           │                                      │
│   └──────────────┘                                       │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**关键理解**：
- **案件**是结构化数据（案号、当事人、金额、结论），存在 NocoDB 表格里，可以按字段搜索、筛选、统计
- **文档**是原始文件（PDF 判决书、起诉状），存在 Paperless-ngx 里，OCR 后全文可搜索
- **规则**是经验积累（检查清单、审核要点），存在 NocoDB 表格里，按案由自动匹配

```
          └───────────────────────────────────────...┘
```

### 3.2 为什么是两个系统，不是一个

| 需求 | 用什么满足 | 为什么不用一个系统 |
|------|-----------|-------------------|
| 按字段精确搜索（"赔偿金额>10万的著作权案件"） | NocoDB | Paperless-ngx 做不到结构化字段搜索 |
| 按关键词全文搜索文档内容 | Paperless-ngx | NocoDB 做不到 PDF 内容全文检索 |
| 检查清单逐项对照 | NocoDB | Paperless-ngx 不支持这种交互 |
| PDF 自动 OCR 识别 | Paperless-ngx | NocoDB 不支持 |
| 经验规则按案由自动匹配 | NocoDB | Paperless-ngx 不支持关联逻辑 |

两个系统各司其职，文员使用时只是打开两个浏览器标签页。

### 3.3 资源需求

| 组件 | 容器数 | 内存 | 磁盘 |
|------|--------|------|------|
| NocoDB (Node.js) | 1 | ~300MB | - |
| NocoDB PostgreSQL | 1 | ~200MB | 数据目录 |
| Paperless-ngx (Web) | 1 | ~500MB | - |
| Paperless-ngx PostgreSQL | 1 | ~200MB | 数据目录 |
| Paperless-ngx Redis | 1 | ~50MB | - |
| Paperless-ngx Gotenberg | 1 | ~200MB | - |
| Paperless-ngx Tika | 1 | ~500MB | - |
| **合计** | **7** | **~2GB** | **~10GB 起** |

> **补充**：Word 批注预处理脚本不需要常驻容器，按需手动执行或 cron 定时触发，不额外占用资源。

#### 长文本字段容量说明 ⚠️

NocoDB 的 `LongText` 字段限制为 **100,000 字符**（约 5 万中文字，约 25-30 页 A4 纸）。

| 字段 | 典型内容 | 是否够用 |
|------|---------|---------|
| `事实摘要` | 500 字概述 | ✅ 绰绰有余 |
| `适用法条` | 几条法条原文 | ✅ 够用 |
| `争议焦点` | 2-3 个争议点描述 | ✅ 够用 |
| `审核结论` | 审核意见，500-1000 字 | ✅ 够用 |
| `备注` | 补充说明 | ✅ 够用 |

**如果未来需要更长的内容**（如完整判决书全文），解决方案：
- 完整文档存 Paperless-ngx（无长度限制），NocoDB 只存摘要
- 或拆分为多条记录（如按段落拆分到子表）
- 或通过 NocoDB `NC_NON_ATTACHMENT_FIELD_SIZE` 环境变量调大字段上限（注意：该变量存在已知兼容性问题，GitHub issue #11901，需实测验证后再采用）

> **调研确认（2026-08）**：NocoDB 的 100,000 字符限制是**应用层强制**的，与底层数据库无关。即使后端是 PostgreSQL 的 `TEXT` 类型（底层无长度限制），NocoDB UI/API 仍会拦截超过 100K 的写入。因此"换后端即解除限制"的说法不成立，本方案以 Paperless-ngx 承载长文档为准。

### 4.3 规则与清单的生成方式 ⚠️ 重要

**规则和清单是人工定义和持续积累的，系统不做自动扫描归纳。**

```
┌─────────────────────────────────────────────────────────┐
│ 阶段 1：初始定义（系统上线前，管理员做）                     │
│                                                          │
│ 资深法务人员凭经验写出初始检查清单和规则：                    │
│  • "著作权纠纷每次审核都要看权属、侵权、赔偿三个维度"         │
│  • "把这 7 个必查项写成检查清单，新人照着做"                 │
│  • "根据历史判例，图片侵权赔偿一般 3K-10K，写入规则"         │
│                                                          │
│ → 管理员在 NocoDB 中手动录入 checklists 和 rules 表         │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│ 阶段 2：日常使用中积累（文员操作）                          │
│                                                          │
│ 文员审核案件 → 发现清单没覆盖的新要点 → 手动添加规则         │
│                                                          │
│ 例如：                                                    │
│  "这个案子涉及 AI 生成内容的版权，之前的清单没有这个，       │
│   我在规则表里加一条：AI 生成内容需确认训练数据来源"          │
│                                                          │
│ → 文员在 NocoDB rules 表中新增记录，关联来源案件             │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│ 阶段 3：定期整理（管理员定期做）                            │
│                                                          │
│ 规则越来越多 → 管理员定期 review → 合并重复规则             │
│ → 将成熟规则补充到检查清单 → 更新清单版本号                  │
│ → 标记过时规则为"已过时"                                   │
└─────────────────────────────────────────────────────────┘
```

**系统不会自动做的事**：
- ❌ 不会自动读 PDF 提取规则
- ❌ 不会分析案件模式自动归纳
- ❌ 不会用 AI 生成检查清单
- ❌ 不会自动推荐规则

**系统会做的事（都是数据库操作，不是 AI）**：
- ✅ 筛选：选择"案由=著作权纠纷" → 自动显示适用该案由的清单
- ✅ 关联：查看检查项时 → 可点击跳转到"来源案件"
- ✅ 搜索：关键词搜索规则名称和内容
- ✅ 追溯：审核记录可追溯到具体检查项和案件

### 4.4 NocoDB 视图设计

NocoDB 支持给同一张表创建多个"视图"（类似 Excel 的筛选视图），文员不用自己写筛选条件：

| 视图名 | 说明 | 预设筛选 |
|--------|------|---------|
| 全部案件 | 默认视图 | 无 |
| 审核中案件 | 只看待审核的 | 案件状态 = 审核中 |
| 著作权纠纷 | 按案由筛选 | 案由 = 著作权纠纷 |
| 本月新收 | 按时间筛选 | 收案日期 = 本月 |
| 赔偿金额一览 | 重点看金额 | 显示：案号、案由、诉求金额、判决金额、执行金额 |
| 高风险案件 | 关注风险 | 风险等级 = 高 |
| 紧急案件 | 优先处理 | 紧急程度 = 高 |

## 5. Paperless-ngx 文档管理设计

### 5.1 标签体系

预设标签，文员上传文档时勾选：

| 标签类别 | 标签示例 |
|---------|---------|
| 文档类型 | 判决书、起诉状、证据清单、鉴定报告、裁定书、代理词 |
| 案件类型 | 著作权纠纷、商标纠纷、专利纠纷、不正当竞争 |
| 审级 | 一审、二审、再审 |
| 年份 | 2024、2025、2026 |

> **说明**：Paperless-ngx **v2.19+ 已支持嵌套标签（nested tags）**，可为标签建立父子层级。上表的"类别"可通过嵌套标签实现（如 `案件类型 ▸ 著作权纠纷`）。若部署版本低于 v2.19，则退化为扁平标签，此时"类别"仅作为命名约定（用前缀区分，如 `类型:判决书`），需在部署时确认实际版本能力。

### 5.2 文档上传流程

```
文员拖拽 PDF → Paperless-ngx 接收
      │
      ▼
Tika 提取文本（原生 PDF）
      │
      ▼

      │
      ▼

      │
      ▼

      │
      ▼

```

> **中文 OCR 说明**：Paperless-ngx 官方镜像默认只包含英文/德/意/西/法语言包，**不含简体中文**。本项目部署使用社区中文镜像 `liuweitao/paperless-ngx`（在官方镜像基础上内置简繁中文 OCR 支持），并配置 `PAPERLESS_OCR_LANGUAGE=chi_sim+eng`、`PAPERLESS_OCR_LANGUAGES=chi_sim eng`。若坚持使用官方镜像，需自行安装 `tesseract-ocr-chi-sim` 语言包，否则中文扫描件无法识别。

### 5.4 Word 文档批注/修订处理 ⚠️ 重要

**问题**：法务审核中，Word 文档的批注（Comments）和修订（Track Changes）是核心经验载体。资深律师在文档上批注的修改意见，本身就是最宝贵的规则来源。

**Paperless-ngx 的局限**：Apache Tika 可以提取 Word 文档正文，但**不能可靠地提取批注内容和修订痕迹**。Paperless-ngx 适合处理"最终版"静态文档，不适合处理带批注的审阅稿。

**解决方案**：增加一个轻量级 Python 预处理脚本，在文档入库前自动提取批注。

```
Word 文档（含批注）上传
        │
        ▼
┌──────────────────────────────────────────┐
│ 预处理脚本（python-docx）                  │
│                                           │
│ 1. 提取文档正文（给 Paperless-ngx 索引）    │
│ 2. 提取所有批注：                           │
│    • 批注文本（comment.text）              │
│    • 批注作者（comment.author）            │
│    • 批注时间（comment.date）              │
│    • 引用的原文段落（comment-reference）    │
│ 3. 提取修订痕迹（Track Changes）:          │
│    • 插入的文本 / 删除的文本                │
│    • 修订作者 / 修订时间                    │
│    → 使用 docx-revisions 库               │
│                                           │
│ 输出：                                     │
│  • 清洁版文档 → Paperless-ngx 入库         │
│  • 批注结构化数据 → NocoDB 批注记录表       │
└──────────┬───────────────────────────────┘
           │
     ┌─────▼──────┐      ┌──────────────────┐
     │ Paperless  │      │  NocoDB          │
     │ 清洁版文档  │      │ 批注记录表（新增） │
     │ 全文可搜索  │      │ 可搜索、可关联案件 │
     └────────────┘      └──────────────────┘
```

#### 批注记录表 `comment_records`

> 表结构见 4.1 节**表 6**，此处不再重复。批注/修订提取的数据统一写入该表，与案件、规则关联后可检索、可追溯。

**技术实现**：
- `python-docx` 库：提取批注（comments），包括文本、作者、时间、引用段落
- `docx-revisions` 库：提取修订痕迹（Track Changes），包括插入/删除的文本和作者
- 脚本量：约 100-200 行 Python
- 部署方式：独立 Python 脚本，通过 cron 或手动触发，不嵌入任何现有系统

> **注意**：这是整个方案中**唯一的自研代码**（约 200 行），其余全部使用开源成熟系统。

#### 关于"文档↔案件"的关联方式（弱关联）

NocoDB 与 Paperless-ngx 是两个独立系统，案件与文档之间通过 NocoDB 案件表的 `关联文档` 字段**手工粘贴 Paperless 链接**实现"弱关联"，不建立数据库级外键。这意味着：

- 依赖文员主动复制/粘贴 URL，存在漏贴、错贴的可能；
- Paperless 中文档改名/移动后，链接可能失效；
- **缓解措施**：① 在 `关联文档` 字段粘贴时附带文档标题，便于核对；② 定期（如每月）人工抽查链接是否有效；③ 若后续需要强关联，可升级为用 Paperless REST API 按案号自动回填链接（v3 不做，列为远期）。

#### 关于"逐项审核"的操作体验

审核动作发生在 NocoDB 的 `review_records` 表，每条检查项一行。NocoDB 采用**表格（Grid）/表单（Form）视图**，文员逐行填写"检查结果"下拉（符合/不符合/不适用/待确认）并补充审核备注。为降低操作门槛，建议：

- 为 `review_records` 建"按案件筛选"的视图（详见 4.4 视图设计思路），文员打开即是本案件的待审项；
- 详细设计阶段出一个**审核界面原型**（表格 + 下拉），确认文员容易上手后再固化流程。

| PostgreSQL (NocoDB) | 机器 C | 无 | 需开放 5432 端口 |

| Redis / Gotenberg / Tika | 机器 B 或独立 | 无 | 独立服务，可任意拆分 |

**分布式部署的关键约束**：
- 所有机器需在同一内网（或通过 VPN 互联）
- 数据库端口（5432）、Redis（6379）需要开放
- 不建议将 Gotenberg 和 Tika 单独拆分（它们是 Paperless-ngx 的内部依赖，直接通信延迟最低）

### 7.4 Docker Compose 配置

> ⚠️ **安全提醒**：以下 compose 中的数据库密码（`nocodb123` / `paperless123`）为**示例密码**，正式部署前必须修改为强密码，并同步更新 `NC_DB` 连接串与备份脚本（8.2 节）中的对应值。建议使用环境变量注入（如 `${NC_DB_PASSWORD}`）避免明文。

#### NocoDB（1 个容器）

```yaml
# /opt/nocodb/docker-compose.yml
version: '3.8'
services:
  nocodb:
    image: nocodb/nocodb:latest
    container_name: nocodb
    restart: always
    ports:
      - "8090:8080"
    environment:
      - NC_DB=pg://db:5432?u=postgres&p=nocodb123&d=nocodb
      - TZ=Asia/Shanghai
    volumes:
      - /opt/nocodb/data:/usr/app/data
    depends_on:
      - db

  db:
    image: postgres:16
    container_name: nocodb-db
    restart: always
    environment:
      - POSTGRES_USER=postgres
      - POSTGRES_PASSWORD=nocodb123
      - POSTGRES_DB=nocodb
    volumes:
      - /opt/nocodb/pgdata:/var/lib/postgresql/data
```

#### Paperless-ngx（5 个容器）

```yaml
# /opt/paperless/docker-compose.yml
version: '3.8'
services:
  broker:
    image: redis:7
    container_name: paperless-redis
    restart: always

  db:
    image: postgres:16
    container_name: paperless-db
    restart: always
    environment:
      - POSTGRES_USER=paperless
      - POSTGRES_PASSWORD=paperless123
      - POSTGRES_DB=paperless
    volumes:
      - /opt/paperless/pgdata:/var/lib/postgresql/data

  webserver:
    image: liuweitao/paperless-ngx:latest
    container_name: paperless-web
    restart: always
    ports:
      - "8091:8000"
    environment:
      - PAPERLESS_REDIS=redis://broker:6379
      - PAPERLESS_DBHOST=db
      - PAPERLESS_DBUSER=paperless
      - PAPERLESS_DBPASS=paperless123
      - PAPERLESS_DBPORT=5432
      - PAPERLESS_TIKA_ENABLED=1
      - PAPERLESS_TIKA_GOTENBERG_ENDPOINT=http://gotenberg:3000
      - PAPERLESS_TIKA_ENDPOINT=http://tika:9998
      - PAPERLESS_OCR_LANGUAGE=chi_sim+eng
      - PAPERLESS_OCR_LANGUAGES=chi_sim eng
      - PAPERLESS_TIME_ZONE=Asia/Shanghai
      - PAPERLESS_CONSUMER_POLLING=60
    volumes:
      - /opt/paperless/data:/usr/src/paperless/data
      - /opt/paperless/media:/usr/src/paperless/media
      - /opt/paperless/consume:/usr/src/paperless/consume
      - /opt/paperless/export:/usr/src/paperless/export
    depends_on:
      - broker
      - db

  gotenberg:
    image: gotenberg/gotenberg:8
    container_name: paperless-gotenberg
    restart: always
    command:
      - "gotenberg"
      - "--chromium-disable-routes=true"

  tika:
    image: apache/tika:latest
    container_name: paperless-tika
    restart: always
```

## 8. 运维方案

### 8.1 日常操作

|------|------|

| 启动 Paperless | `cd /opt/paperless && docker compose up -d` |

| 查看状态 | `docker ps --filter "name=nocodb" --filter "name=paperless"` |
| 查看日志 | `docker compose logs -f --tail=100` |

### 8.2 备份

```bash
#!/bin/bash
# 备份脚本：/opt/backup.sh
DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_DIR=/opt/backups/$DATE

mkdir -p $BACKUP_DIR

# 备份 NocoDB PostgreSQL
cd /opt/nocodb
docker compose exec -T db pg_dump -U postgres nocodb > $BACKUP_DIR/nocodb.sql

# 备份 Paperless-ngx PostgreSQL
cd /opt/paperless
docker compose exec -T db pg_dump -U paperless paperless > $BACKUP_DIR/paperless.sql

# 备份 Paperless-ngx 文档
tar -czf $BACKUP_DIR/paperless_media.tar.gz /opt/paperless/media

# 保留最近 30 天
find /opt/backups -type d -mtime +30 -exec rm -rf {} \;

echo "备份完成: $BACKUP_DIR"
```

设置 cron 每天凌晨 2 点自动备份：
```
0 2 * * * /opt/backup.sh >> /opt/backups/backup.log 2>&1
```

### 8.3 升级

```bash
# 升级 NocoDB
cd /opt/nocodb
docker compose pull
docker compose up -d

# 升级 Paperless-ngx
cd /opt/paperless
docker compose pull
docker compose up -d
```

### 8.4 监控

```bash
# 资源占用
docker stats nocodb nocodb-db paperless-web paperless-db

# 磁盘使用
du -sh /opt/nocodb /opt/paperless
```

## 10. 待确认事项

在进入详细设计前，请确认：

| # | 问题 | 说明 |
|---|------|------|
| 1 | **表结构是否合理？** | 第 4 节共 6 张表（含新增的批注记录表），字段是否需要增减 |
| 2 | **长文本字段是否够用？** | NocoDB LongText 上限 100K 字符为**应用层强制**（调研已确认，与后端数据库无关），当前够用；长期超长内容走 Paperless-ngx |
| 3 | **Word 批注提取方案是否接受？** | 需 ~200 行 Python 预处理脚本，是唯一的自研代码 |
| 4 | **检查清单由谁维护？** | 初始模板由管理员预设，后续文员可以自己补充吗？ |
| 5 | **是否需要权限控制？** | 所有人看到所有案件？还是不同人不同权限？v3 默认不做权限 |
| 6 | **是否需要统计报表？** | 如案件类型分布、赔偿金额趋势等，v3 默认不做 |
| 7 | **是否接受两个系统分开使用？** | 还是需要一个统一入口？ |
| 8 | **端口规划是否确认？** | 8090（NocoDB）/ 8091（Paperless-ngx），内部端口不暴露 |
| 9 | **是否可以开始部署？** | 先部署空系统，再逐步录入数据？ |
| 10 | **中文 OCR 方案是否接受社区镜像？** | 官方镜像不含简体中文 OCR 包，方案采用社区镜像 `liuweitao/paperless-ngx`（含 chi_sim）；若要求官方镜像，需额外安装 tesseract 语言包并自建镜像 |
| 11 | **是否需要标签层级？** | Paperless-ngx v2.19+ 已支持嵌套标签（父子层级）；当前方案用"标签前缀"模拟，是否需要启用原生层级？ |
| 12 | **"文档↔案件"弱关联是否接受？** | 文档与案件通过"文件名前缀约定 + NocoDB 关联文档字段"手动维护关联（详见 6.1），不做自动匹配；是否接受？ |
