## 1. 系统架构总览

### 1.1 进程与分层

```
┌──────────────────────────────────────────────────────────────┐
│ 前端 SPA（React/Vite，Nginx 静态托管，独立容器）                │
└──────────────────────────┬───────────────────────────────────┘
                           │ HTTP/JSON（REST）
┌──────────────────────────▼───────────────────────────────────┐
│ FastAPI 应用进程（单进程 + 线程池，uvicorn 1 worker）           │
│ ┌───────────┐ ┌───────────┐ ┌──────────────────────────────┐  │
│ │ API 层 router│ │ 业务服务层 │ │ AI 集成层（ModeA 管道/MCP 服务）│  │
│ └───────────┘ └───────────┘ └──────────────────────────────┘  │
│ ┌───────────┐ ┌───────────┐ ┌──────────────────────────────┐  │
│ │ 同步引擎  │ │ 清洗管道  │ │ 指标口径引擎（纯函数计算）        │  │
│ └───────────┘ └───────────┘ └──────────────────────────────┘  │
└──────────────────────────┬───────────────────────────────────┘
                           │ SQLAlchemy 2.x（SQLite WAL）
┌──────────────────────────▼───────────────────────────────────┐
│ SQLite 单文件 + WAL 模式（app.db）                              │
│ 表: cases / songs / song_case / dicts / rules / metrics /      │
│     sync_jobs / sync_batches / audit_logs / tags / tag_links / │
│     external_cases / saved_views / reports / settings          │
└───────────────────────────────────────────────────────────────┘
外部依赖: 飞书开放平台（只读）· LLM API（Mode A）· 案例库/法规 API（三源，Phase2+）· APScheduler（03:00）
```

- **单进程设计理由**：单用户工作台，638 条数据；避免多 worker 导致的 SQLite 写锁竞争与同步竞态；
- **写读分离保证**：同步写入 staging 前缀表 → 事务内 `INSERT OR REPLACE` 原子换入正式表；查询只读正式表，永不被写事务阻塞（WAL 读快照）；
- **任务并发约束**：同一时间只允许 1 个同步任务（`sync_lock` 卡控制），重复触发返回 409。

### 1.2 技术选型落地清单（SPEC 6.1 定稿）

| 层 | 定稿 | 备注 |
|----|------|------|
| 框架 | FastAPI 0.11x + Pydantic v2 | 自动 OpenAPI 文档（前端 TS types 生成源） |
| ORM | SQLAlchemy 2.x（Declarative + Mapped） | 显式类型；模型与迁移一体（单文件 app.db 重建即迁移，Phase 0 提供 `alembic` 可选） |

### 2.2 派生与清洗约定

- **三列原则**：原始值（`*_raw` 或原列）与清洗值（规范列）并存；清洗规则只允许「新增 derived 列 / 规范化原列并留 raw」，**禁止原地覆盖丢原文**；
- **全局 `dirty_flags`**：每行命中哪几条规则（规则 id 列表），前端角标与「脏数据清单」都从它来；
- **回放**：`audit_logs` 记录每条「规则×记录×原值×新值×时间×版本」，支持按规则版本回滚（UPDATE 回原值并重跑后续规则）。

## 3. 同步引擎（SPEC 6.2 落地）

### 3.1 运行模式

| 模式 | 触发 | 说明 |
|------|------|------|
| 天级增量 | APScheduler 03:00 | updated_at 窗口（上次 last_sync → now）+ 游标双保险 |
| 手动全量 | API `POST /sync/run?type=full` | 全表重拉，幂等（record_id upsert） |
| 手动增量 | API `POST /sync/run?type=incremental` | |
| 单条刷新 | API `POST /sync/run?type=record&id=` | 详情页触发，1 请求/条 |

### 3.2 同步流程（7 步，含失败恢复）

```
1. 加锁（sync_lock KV；已存在且未过期 → 409）
2. 元数据获取: GET /bitable/v1/apps/{app}/tables/{table} → 35 字段 schema
   （首次运行全量拉 schema 入 enum_dicts 基座；后续检测到字段变更 → 版本号 +1 并告警）
3. 分页拉取记录: GET /bitable/v1/apps/{app}/tables/{table}/records?page_size=100
   - 令牌桶限速 3 QPS（20 QPS 上限的 15% 余量给其他请求）; 失败指数退避(1s/4s/16s) 3 次
   - 增量模式: 服务端筛选 updated_at >= last_sync（字段筛选下沉）或本地 hash 比对
   - 游标失效（page_token 过期）→ 放弃分页，切「全量增量窗口」重拉（记录数 638 上限下代价可忽略）
4. 关联展开:
   - DuplexLink（涉及歌曲清单）: 全量拉 songs 表 → 建 song_case 映射（composer/member 解析）
   - SingleLink（父记录）: 记录内包含父 record_id → parent_record_id
   - User 字段: 解析 user_id/name → users 缓存（反查 open_id→姓名，按需批量）
5. 公式字段: 直接采用 API 返回 value（support_rate/per_song_amount/song_count），
   本地以「口径契约」复刻校验（误差 >0.01 时告警留痕，不阻断）
6. 写 staging（表名 `staging_*`）→ 校验行数/主键完整性 → 事务原子换入正式表
   （DELETE 不存在记录标注归档时间 archive_at，**不物理删**，保审计可回放）
7. 写 job/batch 日志；清除锁；向飞书群发通知（可选，失败时）
```

### 3.3 限频与并发（research/03 结论落实）

- 全量 638 条 ≈ 7 页请求 + songs ≈ 2 + User 反查 ≤8 → 全程 <30 请求，20 QPS 限制下理论 <2 分钟；
- 令牌桶 3 QPS 上限；并发 1；重试 3 次（1s/4s/16s + 抖动 ±20%）；
- 同步期间 API 全部可读（写读分离），前端状态条轮询 `GET /sync/status`。

### 3.4 增量窗口与对账

- `sync_jobs.last_sync_at` 驱动增量；每次任务结束即写，应用重启丢失的窗口由「补跑」（下次运行时跨窗口全拉比对 hash）兜底；
- 每任务对账：飞书 total vs 本地 upsert 数，差异>0 记 error_brief 并告警。

## 4. 清洗管道（P0 前置，SPEC 6.3 落地）

### 4.1 管道执行模型

```
源记录 → [规则链按 priority 顺序执行] → 产出（规范列 + *_raw + dirty_flags + 命中明细入 audit）
规则链 = 全局规则 × 目标字段规则（每字段命中首条即标记，多条可叠加）
执行单位 = sync_jobs 内同步完成后的自动阶段（clean_pipeline），也支持手动「重跑全部」
```

### 4.2 首版内置规则（对应需求 4.2 脏数据清单）

| # | 规则类型 | 目标字段 | 实现要点 |
|---|----------|----------|----------|
| R01 | extract_year | year | 正则 `(19|20)\d{2}`（含「年」后缀/空格）→ INT；失败走 accept_date.year；仍失败 → year=-1 + dirty |
| R02 | de_dup 甄别 | plaintiff | 值∈case_status 枚举 或 匹配 `^（?\(\d{4}\)?.*号$` → 入 dirty 清单 + 置待确认（不自动改值，人工确认） |
| R03 | company_map | defendant | company_map 表命中替换 canonical；未命中但含关键词（侵权纠纷等案由词）→ 隔离 + dirty |
| R04 | split_court | court | 含「仲裁委员会/仲裁委」→ 剥离至 arbitration_org；长度异常/含案由词 → dirty |
| R05 | normalize_enum | 全部枚举字段 | 选项值 → 别名表映射（结案原因「原告撤诉(重复)」并入唯一值；收案年份 14 项 → 4 位年） |
| R06 | regex_replace | case_no | 全角括号→半角？否——统一为全角规范「（xx）」；去换行/首尾空白；缺「号」→ 按正则补（如结尾无号则 +“号”）仅限合法格式 |
| R07 | amount_guard | amount/pay_amount | 负值→NULL+dirty；pay_amount>amount×10 超界标记（不自动改） |
| R08 | de_dup | resolve | 重复枚举项归并历史值（去重 id 指向 canonical） |
| R09 | infer_fee | lawyer_fee | 枚举错配：按「resolve×payer」推断 `fee_nature`（诉讼费/律师费/和解金/判赔金）入 derived；**同时向飞书侧提单字段改造（Phase 0 阻塞项），改造完成后取消推断** |
| R10 | null_mark | 全部 | 空值标 NULL 不显示 0；support_rate 除零 → NULL + 「标的缺失」标记 |

### 4.3 清洗可观测性

- `GET /api/v1/dicts/dirty-items`：待人工确认清单（疑似值/建议值/来源案件数/采纳/忽略）；
- 「采纳」写入 enum_dicts.aliases / company_map，全库重跑受影响规则（后台任务）；
- 每次重跑生成规则版本快照（clean_rules.version），回滚 = 恢复上一版本快照 + 重跑；
- 脏数据概览卡（/admin/dicts 首页）：按字段计数、覆盖规则、待确认数。

## 5. 指标口径引擎

### 5.1 计算模型

- 每指标 = `metric_defs.formula_sql` 纯函数化 + 参数（筛选条件、口径版本）；
- 前端图表/卡片请求 `POST /api/v1/stats/guard`（通用聚合查询：`{metric, filters, group_by, version}`）→ 后端解析 metric_defs 执行 → 返回 `{value, sample_n, footnote}`；
- **样本计数与脚注强制随值返回**，前端渲染 tooltip/表格脚注（SPEC 5.4 落地）；
- 口径版本切换：`settings.current_metric_versions` KV，变更后前端全局 store 触发重取。

### 5.2 8 指标 SQL 定义（口径操作化，对应需求 4.3）

```sql
-- 胜诉率A（胜败二级，不含和解/撤诉/执行）
WITH t AS (SELECT resolve FROM cases WHERE {{filters}} AND resolve IS NOT NULL)
SELECT (SELECT COUNT(*) FROM t WHERE resolve IN ('胜诉','驳回上诉维持原判','判决驳回对雷石的诉求',
        '裁定驳回雷石的诉讼请求','裁定驳回对雷石的诉讼请求'))
     / CAST(NULLIF((SELECT COUNT(*) FROM t WHERE resolve IN (上述胜集) OR resolve='判赔'),0) AS REAL) AS win_rate_a;

-- 胜诉率B（含和解）
分母追加 '双方和解'，分子追加 '双方和解'

-- 对方诉求支持率（加权，沿用飞书公式同构）
SELECT SUM(pay_amount)/NULLIF(SUM(amount),0) FROM cases WHERE {{filters}} AND amount>0 AND pay_amount IS NOT NULL;

-- 判赔率（仅判赔子集）
SELECT AVG(pay_amount/amount) FROM cases WHERE resolve='判赔' AND amount>0;

-- 单曲判赔（均值/中位数）
SELECT AVG(per_song_amount), PERCENTILE: per_song_amount 中位数 FROM cases WHERE song_count>0;

-- 结案周期（天，中位数/均值）
SELECT AVG((close_date-accept_date)/86400000.0) FROM cases WHERE accept_date IS NOT NULL AND close_date IS NOT NULL;

-- 系列案系数
SELECT AVG(merged_count), 分布直方 FROM cases;

-- 在办案件数
SELECT COUNT(*) FROM cases WHERE case_status NOT IN ('已结案');
```

### 5.3 契约：飞书公式 vs 本地复刻（SPEC 风险「公式失真」消解）

| 公式字段 | 飞书侧 | 本地复刻 | 校验 |
|----------|--------|----------|------|
| 对方诉求支持率 | =支付总金额/标的 | SUM(pay)/SUM(amount)（加权场景）| 同步时逐条对比 API 值，误差>0.01 → dirty |
| 单曲判赔/和解金额 | =支付总金额/涉案歌曲数量 | 同公式 | 同上 |
| 涉案歌曲数量 | =COUNTA(歌曲清单) | COUNT(song_case) | 同上 |

## 6. API 设计（REST，OpenAPI 自动生成）

### 6.1 通用约定

- 前缀 `/api/v1`；响应包 `{code:0, data, meta:{page, total, footnote}}`；
- 错误：HTTP 4xx/5xx + `{code, message, detail}`；500 时 detail 带 request_id（前端错误态展示）；
- 认证：单用户 Token（env `APP_TOKEN`，前端登录页一次换取），无 RBAC；
- 审计中间件：写操作（POST/PUT/DELETE）与导出自动记 audit_logs（含 body 摘要）；查询类在 `/admin/audit` 留存（可配置抽样率）。

### 6.2 端点清单（SPEC 6.5 展开定稿）

**元数据与字典**

```
GET  /api/v1/metadata          → {fields:[{name,type,enum,label,clean_level,rawable}], enums, metric_versions, sync:{last_sync_at,status}}
GET  /api/v1/enums/{field}     → 枚举+别名+颜色（筛选器数据源）
```

**检索与案件**

```
POST /api/v1/search            body:{q?, filters:[{field,op,in|range|eq|contains}], sorts, page, page_size, columns?}
                               → {total, rows:[...], footnote}
GET  /api/v1/cases/{id}        → 完整五区数据（含 derived、raw、关联、审计摘要、dirty_flags）
GET  /api/v1/cases/{id}/raw    → 原始值快照（原始视图切换）
POST /api/v1/cases/batch       body:{ids, action:export|tag, tag?} → 批量操作（审计）
GET  /api/v1/cases/{id}/similar?top=10 → S8 相似案
```

**统计（口径引擎统一入口）**

```
POST /api/v1/stats/guard       → 通用聚合（§5.1）；group_by 支持 year/biz_line/cause/resolve/payer/month
GET  /api/v1/stats/overview?version=   → 总览页 4 卡 + 趋势 + 构成 + 日程（一次返回，前端缓存 60s）
GET  /api/v1/stats/party?name=         → 画像卡指标 + 系列（明细走 search）
GET  /api/v1/stats/songs?...           → 歌曲聚合 + 单曲详情
GET  /api/v1/stats/fees?year=          → 费用归集（月度×性质×主体）
```

**同步与系统**

```
POST /api/v1/sync/run {type: full|incremental|record, id?}     / 重复触发 409
GET  /api/v1/sync/status     → {running, progress, last:{at,result,delta}, next_at}
GET  /api/v1/sync/logs?      → job/batch 列表
GET  /api/v1/dicts | POST /api/v1/dicts | POST /api/v1/dicts/test {sample}{ → 规则测试
GET  /api/v1/dicts/dirty-items  POST /api/v1/dicts/dirty-items/{id} {action:adopt|ignore|edit}
POST /api/v1/export {scope, columns, format, with_footnote} → 异步任务+下载
GET  /api/v1/audit?...   GET /api/v1/settings  PUT /api/v1/settings/{k}
```

**AI（Mode A）**

```
POST /api/v1/ai/query {session_id?, question} → SSE 流（分段: 检索证据 → 回答 → 脚注 → 建议追问）
GET  /api/v1/ai/sessions  GET /api/v1/ai/sessions/{id}
```

### 6.3 检索实现（FTS5）

```
FTS 影子表 fts_notes(case_id, case_no, plaintiff, defendant, court, notes, judge)
查询: q 分词（jieba cut_for_search）→ MATCH 词组 AND 组合 → 高亮片段 snippet()
过滤: 结构化字段走 SQL 条件（与 FTS 交集）
排序: 相关性(rank) 或 显式 sort 覆盖；混合排序 = 过滤后 sort
性能: 638 行 `q` 命中 <10ms；10 万行 <100ms（实测基准目标）
```

## 7. AI 集成与三源交叉验证（Phase 2/3）

### 7.1 Mode A 对话管道（SPEC 7.1 落地）

```
question → ① 意图分类（query_data/query_doc/unsupported）
        → ② 参数抽取（LLM 结构化输出: {year, party, cause, biz, amount_range, metric} 或走规则兜底）
        → ③ 检索内核执行（复用 §6.3 + stats/guard）
        → ④ 证据组装（top_k 记录摘要 + 聚合结果 + 口径）
        → ⑤ LLM 生成（附 prompt 模板: 强制“只依据检索证据回答，无证据则明说”）
        → ⑥ 输出（SSE: 证据块 → 润色块 → 脚注块 → 建议追问 chips）
```

- 回退：意图分类可用规则管线（关键词膨胀表）当 LLM 不可达；检索失败 → 如实回答「本地库暂无数据」；
- 幻觉抑制：生成 prompt 注入「证据清单」且禁止输出证据外数字；输出后做「数字一致性校验」（回答中金额/件数在证据集内存在，否则标注）；
- 会话：session 持久化（sqlite），追问自动继承上下文条件。

### 7.2 三源交叉验证（SPEC 4.4 落地）

| 源 | 接入 | 状态 |
|----|------|------|
| 📂 本地历史库 | §6.3 内核 | Phase 1 |
| ⚖️ 案例/判决 | research/01 选型：首推人民法院案例库（免费、rmcourt 官网实测 3927 篇、支持高级检索/收藏）为 **T1 半自动源**；北大法宝等商业 API 为 T2（Phase 2 立项商务决策）；入库 `external_cases`（案例标题/案号/法院/年份/裁判要旨/URL），**人工复核后入库**（禁批量爬虫） | Phase 2 阻塞项 |
| 📜 法律法规 | 国家法律法规数据库 flk.npc.gov.cn 等；模式=模板锚定条文（如著作权法 §53）+ 外链，**不全文抓取** | Phase 2 |

- Mode A/B 输出的脚注结构统一（字段：source_type / count / link / note）；
- 缺源显示：任一源 count=0 → 输出「缺源：xxx」灰字（SPEC 4.4 强制）。

### 7.3 Mode B · MCP 服务（SPEC 8 落地）

- 交付物：独立 Python 服务 `mcp_server.py`（FastMCP in-process，与 API 同进程可切独立容器）；
- 暴露 8 工具（只读）：

```
case_report_year(params.year_range, resolve_set)        → T1 结案情况
party_report(name, biz_line)                            → T2 对手方诉权
song_report(song, artist, year)                         → T3 单曲判赔
win_rate_report(year, version)                          → T4 胜诉率
fee_report(year, payer)                                 → T5 费用汇总
similar_cases(cause, amount_range, defendant)           → T6 同类案
court_agenda(week_range)                                → T7 开庭周报
authorize_search(domain_declaration)                    → 授权检查（记录审计后再执行）
```

- 每工具 = 「参数 Schema(Pydantic) + 检索内核调用 + Markdown 骨架渲染」；返回体统一 `{report_md, footnote: {local, cases, law}, audit_id}`；
- 只读硬约束：工具层无写接口；连接凭据服务端持有，外部 Agent 只见只读数据视图。

## 8. 导出服务

- 统一 `POST /api/v1/export`：scope（当前筛选快照/选中 ids/报告 id）→ 异步任务（`export_jobs` 表）→ 下载；
- CSV：UTF-8 with BOM，首两行注释（导出时间/人/条件摘要/口径脚注），表头规范名；

- 报告类（画像/单曲/费用）：Markdown → HTML → 打印 PDF（浏览器端，§8.3 前端约定配合）。
