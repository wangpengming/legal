## 1. 项目背景与目标

### 1.1 业务背景

我司（雷石/雷客体系）常年面临音乐版权/著作权类诉讼，**自己是被告**的比例高：

- **对手方**：版权方、著作权集体管理组织、词曲作者/经纪公司（原告/上诉人/申请人角色）；
- **被诉对象**：我司终端体系与子公司（KTV 门店、VOD/IPTV/OTT/车载终端、雷客、哇屋等 8 条业务线）；
- **案由高度集中**：侵害作品信息网络传播权纠纷、著作权权属/侵权纠纷、计算机软件著作权许可使用合同纠纷三类占绝对多数，另有劳动争议、租赁、服务合同、执行异议、肖像权、不正当竞争、追偿权、破产程序等少量杂项；
- **案件形态**：同质化「批量系列案」为主——同一版权方（或关联方）对同类终端近乎同一案由批量起诉，实测同一案件记录可合并 1~4+ 个案号，存在「父记录」自关联字段暗示案件树形/分组结构，**合并案件数**字段表明一张表内已有多案合并录入的习惯。

这类案件单案标的/判赔额不高（实测标的多在 1.5 万~77.5 万元区间），但**总量大、周期长、重复劳动多**，历史数据的沉淀价值远大于单案价值。

### 1.2 数据现状（飞书实测结论，2026-08-13 核对）

| 维度 | 实测结果 | 对需求的影响 |
|------|----------|--------------|
| 数据量 | 638 条 / 覆盖 2017~2026 共 10 年 | 单机 SQLite 缓存 + 前端本地分析完全可行，无需大数据组件 |
| 字段规模 | 35 个字段（Text/SingleSelect/MultiSelect/Number/Formula/Lookup/DuplexLink/SingleLink/User/DateTime 多种类型） | 数据字典必须按实测收敛，不能假设 |
| 表内主键 | 「案号」（Text 主字段），**一行可含多个案号**（合并案件数=3 时一行 3 个案号） | 检索与关联设计必须考虑多案号拆分 |
| 关联表 | 「涉及歌曲清单」（DuplexLink），歌曲↔案号多对多；「涉案歌曲-艺人」等为 Lookup 透传 | 歌曲维度分析依赖多表 JOIN，需同步到本地 |
| 指标基座 | 「标的」+「支付总金额」+ 公式字段「对方诉求支持率 = 支付总金额 ÷ 标的」 | 已有公式体系，本地需复刻且契约一致 |
| 业务线 | 8 条：VOD/IPTV·OTT/车载/雷客/人力/哇屋/研发/默霆 | 统计必须支持按业务线下钻 |
| 数据质量 | 脏数据大量存在（详见 4.2） | 清洗是 P0 前置任务，不是可选优化 |
| 决策者 | 个人法务使用，无多角色权限体系 | 无需 RBAC，但需审计与导出 |

### 1.3 痛点（用户视角）

1. **数据只能看不能算**：飞书多维表格能承载记录，但对「某版权方多年累计起诉我司多少件？胜诉率多少？判赔金额趋势？」这类跨字段、跨年份、跨业务线的统计，需要人肉拉表+Excel，周而复始；
2. **同质案件重复分析**：新收到一批批量起诉时，无法瞬间调出「过往同类案子的结案原因分布、判赔区间、常用抗辩效果」，全靠办案人脑内经验；
3. **系列案全貌缺失**：同一版权方 N 个案号分散在多个业务线/年份，缺少「以对手方（版权方）为中心」的整理视图；
4. **胜诉/判赔口径混乱**：表内没有「胜诉率」字段，胜负散落在「结案原因」15 个选项里，且该字段被错误复用（律师代理费选项也取自它），口径无法统一，也就无法安心对外汇报；
5. **网络判决检索能力萎缩**：裁判文书网上网量 2020→2023 年从约 1920 万件降到 511 万件（降幅约 73%），2021 年后检索能力大幅削弱，单靠它做案头调研已不可靠；
6. **费用归属不清**：「支付总金额」含诉讼费、律师费、合理费用混合口径，支付主体有雷石/雷客/诉讼相对方三态，需按业务线/主体归集才能做预算与复盘。

### 1.4 目标

1. **把 638 条历史沉淀变成可检索、可统计、可画像、可对话的一等公民**，一次性建好数据基座；
2. **以「同质化版权批量诉讼」为主轴**，提供从总览→检索→详情→分析→策略/报告的全链路工作台；
3. **两个 AI 模式并存**：系统内置对话（Mode A）+ 外挂本地 AI Agent 通过 MCP 报告模板（Mode B），互相验证，避免单一依赖；
4. **清洗先行**：首版上线前完成字段清洗与口径统一，此后飞书侧数据质量持续治理；
5. **渐进交付**：Phase 1 检索/看板 → Phase 2 分析与画像 → Phase 3 策略与 AI 报告，每阶段可独立验收。

## 2. 用户画像与核心场景

### 2.1 用户画像

| 项 | 画像 |
|----|------|
| 角色 | 公司法务（个人使用，无多级权限） |
| 频次 | 工作台每日打开；批量案件到达期（起诉高峰）高频检索 |
| 关切 | 新案风险预判、历史判赔区间、对手方策略、费用预算、汇报材料 |
| 技水前提 | 懂 Excel/飞书表，不要求懂 SQL；希望「像用 Excel 一样检索，像用 BI 一样看图表」 |
| 反使用模式 | 禁止让用户先导入/整理数据——数据必须自飞书自动同步，只读使用 |

### 2.2 核心场景（S1~S10，全部基于真实业务，替代 SPEC 旧版「买卖合同/劳动争议」占位用例）

**S1 · 新案待办总览（P0）**
> 周一早上，批量起诉到达。用户打开工作台，看到「待处理案件 47 件 / 本月新增 12 件 / 结案率 68% / 本月判赔总额 ¥1.2 万」等数字卡片，以及「最近开庭 5 场」的今日/本周日程卡，第一时间了解态势后决定先处理哪批。

**S2 · 多条件组合检索（P0）**
> 用户想找「2023 年，基础电信/运营商链路，被告含雷客，结案原因含和解」的案子。在全局检索里组合：收案年份=2023、业务线=车载、支付主体=雷客、结案原因=双方和解 → 命中 23 件，一键导出。

**S3 · 案件详情 / 一手卷宗（P0）**
> 打开任一案件，看到完整 35 字段（含公式字段计算值、涉案歌曲清单、关联案号、父记录分组），办案笔记全文可读，字段缺项/脏值有提醒角标，数据来源于飞书的同步时间清晰可查。

**S4 · 版权方（对手方）画像（P1）**
> 选「XX 版权方」，生成一张画像卡：累计起诉件数、各年趋势、案由构成、结案原因分布、平均判赔、单曲判赔区间、当前在办与已了结列表、与我司和解/抗辩史——用于决定新案是和解还是应诉。

**S5 · 业务线/年份风险分析（P1）**
> 按业务线（VOD/车载/雷客…）×年份下钻：哪些业务线是诉讼重灾区？哪年判赔总额最高？按「对方诉求支持率」分布看和解谈判空间。

**S6 · 单曲判赔与歌曲维度（P1）**
> 某首歌曲被多个案号反复起诉。按歌曲聚合，得到单曲判赔均值/中位数、涉案案件数、判赔趋势——支持《单曲判赔报告》与版权采购决策。

**S7 · 费用与支付监控（P1）**
> 全年按支付主体/业务线/费用类型（诉讼费/律师费/和解金）归集支付总金额，形成月度费用看板，支撑预算复盘。

**S8 · 同质案件类推（P2）**
> 拿到一个新案（案由+被告+标的+原告），系统用历史库找出 Top 10 相似案：结案原因分布、判赔区间、办案笔记要点，输出「新案风险提示卡」。

**S9 · AI 对话与交叉验证（P2）**
> 用户问「我们和 XX 版权方的案子最近两年胜诉率如何？」，系统内置 AI（Mode A）先检索本地库给出带数据来源的答复；用户可信度存疑时，要求调取网络判决/案例库交叉验证（⚠️ 网上判决支柱）。

**S10 · 策略分析与报告生成（P2，Mode B 经 MCP）**
> 本地 AI Agent 通过 MCP 报告模板，调用 7 类报告模板（案件结案情况、对手诉权、单曲判赔、胜诉率等），生成可存档报告；报告内每个数字必须标注数据来源（本地库/网上判决/法律法规），无来源数字用「无依据」标记。

### 2.3 场景优先级

| 优先级 | 场景 | 阶段 |
|--------|------|------|
| P0 | S1 总览、S2 检索、S3 详情（含数据同步） | Phase 1 |
| P1 | S4 对手方画像、S5 业务线风险、S6 单曲判赔、S7 费用监控 | Phase 2 |
| P2 | S8 类推、S9 AI 对话、S10 策略与报告 | Phase 3 |

### 3.2 P0 功能明细（Phase 1）

**F1.1 数据同步**
- 来源：飞书多维表格（app_token=`bascnjWi0aitMksjCVkhy9SNVjd` / table_id=`tblCuET1IuQPysak`），自动发现全部 35 字段与 5 张关联/子表；
- 模式：每日 03:00 增量同步（按字段 updated_at 或记录级 offset 游标）+ 手动一键全量 + 详情页单条刷新；
- 要求：同步任务幂等；失败自动重试 3 次；增量窗口可查（last_sync_at / 每表序号）；同步不阻塞查询（读写分离，先写 staging 再原子换表）；
- 验收：模拟断网后重试成功；飞书侧新增一条记录后手动同步 30 秒内可见。

**F1.2 数据清洗**
- 规则存储：SQLite 规则表（规则名/目标字段/匹配模式/替换值/优先级/启用状态），UI 可维护；
- 必须覆盖（首版内置）：公司名归一化（含错别字）、收案年份规范化（14 个混乱选项→4 位年份）、原/被告选项去噪（剔除混入的状态/案号/案由）、受理法院剔除仲裁机构并拆分、案号规范化（补「号」、去换行）、律师代理费字段语义按「结案原因×支付主体」规则迁移；
- 原则：**清洗结果与原始值并存**（derived 列），任何清洗可回滚、可审计、可一键重跑。

**F2.1 态势总览**：4~6 张数字卡 + 年度趋势折线 + 案由构成环形图 + 近期开庭日程卡 + 数据同步状态条。

**F2.2 全局检索**：支持字段：文本（案号/当事人/承办人/笔记全文）、收案年份、收案时间区间、案由（12 项）、案件状态（21 项）、业务线（8 项）、支付主体（3 项）、结案原因（15 项）、标的区间（元）、支付总金额区间、合并案件数、是否含歌曲关联；检索结果即点即开详情。

**F2.3 案件表格**：预估 638~数万行量级，前端虚拟滚动（首屏 < 200ms）；列显隐与固定首列（案号）；多级排序；行内徽标（案由颜色、状态颜色）；支持批量选中后导出/打标；表格与图表联动（表格筛选结果实时反映到总览图表）。

**F2.4 案件详情**：字段分五区：①案件与当事人（案号/关联案号/原被告/案由/法院/状态）②时间轴（收案/开庭/文书/结案）③金额区（标的/支付总金额/对方诉求支持率/单曲判赔）④关联区（涉及歌曲清单、父记录、合并案号）⑤知识区（办案笔记全文、标签、承办人）；每个字段右上角展示「原始值 vs 清洗值」可切换；数据陈旧提示（距上次同步 > 48h 显示提醒条）。

### 3.3 P1 功能明细（Phase 2）

**F3.1 对手方画像**：筛选维度 = 业务线/年份/案由；卡片项 = 累计件数、在办/已结、结案原因分布、判赔总额与均值、单曲判赔区间、和解率、我方支付主体占比；下方案件明细列表可直接下钻 S3。

**F3.2 多维分析**：采用 drill-down（点年份→点业务线→点案由）与多图表联动；指标：件数、标的合计、支付总金额合计、对方诉求支持率均值/中位数、结案周期中位数；图型：堆叠柱（案由×状态）、热力图（业务线×年份件数）。

**F3.3 歌曲维度**：歌曲聚合口径（去重歌曲名→多案号）；指标：涉案件数、判赔均值/中位数/最大/最小、年度趋势、涉案业务线分布；表格支持按歌曲搜索；导出《单曲判赔明细》。

**F3.4 费用看板**：按支付主体（雷石/雷客/诉讼相对方）× 费用性质（诉讼费/律师费/和解金/赔偿金，由规则表映射「支付总金额+结案原因」推断）月度归集，柱状+明细表，支撑预算复盘。

**F3.5 指标口径中心**：集中展示 6 类指标定义（见 4.3），支持「口径版本」切换（如胜诉率的口径A口径B），任何图表底部带口径说明脚注，防误读。

### 3.4 P2 功能明细（Phase 3）

**F5.1 Mode A 对话**：NL→SQL/检索管道（意图解析→参数抽取→本地库检索→生成）；回答强制附「数据来源列表 + 计算口径」；支持追问（换年份/换主体）；置信度低时主动提示人工核实。

**F5.2 Mode B 报告模板**：7 个模板（案件结案情况报告、对手方诉权分析、单曲判赔报告、年度胜诉率报告、费用汇总报告、同类案参考报告、开庭日程周报），每个模板有固定输入参数（JSON Schema）与输出 Markdown/HTML 模板，经 MCP 暴露给外部本地 AI Agent；同时外部 Agent 具备本地数据授权范围（只读），防止误写。

**F5.3 三源交叉验证**：判赔/胜诉类结论支持取「本地历史库 +（调研选型的案例库/权威库 API，见 research/01）+ 法律法规库」三源；任一源不可用时在结论里明确标注「缺源：网上判决」，不得静默忽略。

**F4.2 同质案类推**：相似度 = 案由权重 40% + 业务线 20% + 结案原因 15% + 标的区间 10% + 对手方 10% + 笔记关键词 5%（首版可调阈值），列出 Top10 相似案并提供结案原因分布与判赔区间小结。

### 3.5 需求边界（本期不做）

- 多用户权限体系（RBAC）——单人使用，仅做只读共享；
- 与飞书双向写回（本期只读同步，不做回写；防手滑污染上游表）；
- 合同管理、催款管理——预留扩展位（后续数据源接入），不在本期；
- 全量判决文书原始 PDF 解析归档（本期仅文书关键字段，卷宗系统走 case-intelligence 项目）；
- 移动端 App——本期仅响应式 Web 可用。

### 4.2 数据质量需求（脏数据清单与清洗规则需求）

> 清洗规则作为**需求**提出，规则实现与规则表 Schema 见后端详细设计（docs/03）。

| 目标字段 | 脏数据现象（实测证据） | 清洗规则需求 |
|----------|------------------------|--------------|
| 收案年份 | 14 个选项含公司名/数字/日期 | 对「4 位数字年份（含带年/带空格）」抽取为 INT 年份；非年份值按收案时间兜底；兜底仍不可用则标记 unknown 并红点上报 |

### 4.3 指标口径需求（统一口径词典，覆盖旧 SPEC「胜诉率」悬空问题）

| 指标 | 定义（操作化） | 数据源字段 | 备注 |
|------|----------------|------------|------|
| 胜诉率（口径A·胜败二级） | 胜=结案原因∈{胜诉,驳回上诉维持原判,判决驳回对雷石的诉求,裁定驳回雷石的诉讼请求,裁定驳回对雷石的诉讼请求}; 败=结案原因∈{判赔}; 待定=其余（和解/撤诉/执行类）; 胜诉率=胜/(胜+败) | 结案原因 | 执行类与调解不计入分母的「判决定性」口径 |
| 胜诉率（口径B·含和解） | （胜+双方和解）/（胜+败+双方和解） | 结案原因 | 用于对外宽松口径 |
| 对方诉求支持率 | 支付总金额/标的（均值、中位数、P75） | 公式字段复刻 | 连续指标，优于胜诉率能反映折让空间 |
| 判赔率 | 支付总金额/标的，仅对结案原因=判赔 的子集 | 结案原因+金额 | 判决境口径 |
| 单曲判赔 | 支付总金额/涉案歌曲数量（均值/中位数） | 支付总金额+歌曲计数 | 分母=0 置 NULL |
| 结案周期 | 结案日期−收案时间（天，中位数/均值） | 收案时间+结案日期 | 排除空值并标注覆盖量 |
| 系列案系数 | 合并案件数均值/分布 | 合并案件数 | 批量诉讼规模特征 |
| 在办案件数 | 案件状态∉{已结案} 的计数 | 案件状态 | 看板主数字卡 |

> 口径词典在 UI 有「口径中心」可查阅；任何导出/报告自动携带口径脚注。
