## 1. 背景与目标

### 1.1 背景（修正后）

我司长期卷入**音乐版权/著作权类批量诉讼**：版权方/集体管理组织批量起诉我司终端体系（VOD/IPTV·OTT、车载、雷客、哇屋、人力、研发、默霆等 8 条业务线）侵害作品信息网络传播权等，另有劳动争议、租赁、服务合同等杂项案由。

历史案件沉淀在飞书多维表格「历年诉讼案件总表」中，**实测 638 条、35 字段、覆盖 2017~2026**，并存在「涉及歌曲清单」关联表与「父记录」自关联（系列案树形结构）。

痛点：数据只能查不能算；同质化案件重复分析；系列案缺全貌；胜负口径混乱；网上判决检索能力萎缩；费用归属不清（详见需求文档 1.3）。

### 1.2 目标

1. 数据基座：638 条全量落地本地 SQLite，天级同步，可检索/统计/画像；
2. 业务主轴：以「同质化版权批量诉讼」为中心的全链路工作台（总览→检索→详情→分析→策略/报告）；
3. AI 双模式：内置对话（Mode A，本轮经 OCR 纠偏）+ 外挂本地 AI Agent 经 MCP 报告模板（Mode B）；
4. 清洗先行：脏数据治理是 Phase 1 P0 前置任务；
5. 渐进交付：Phase 1 基座+工作台 → Phase 2 分析 → Phase 3 策略与 AI。

### 1.3 范围

- 本期：诉讼案件只读分析平台（飞书→本地单向同步，无回写）；
- 不做：RBAC、合同/催款模块、卷宗 PDF 全文解析（另立 case-intelligence 项目）、移动 App（本期仅响应式 Web）。

### 3.3 字段清单（35 字段，完整数据字典见需求文档 4.1）

关键结构结论：

- **金额三兄弟**：标的（N，元）→ 对方诉求支持率（F=支付总金额/标的）；支付总金额（N，元，含诉讼费/合理费用混合口径）→ 单曲判赔/和解金额（F=支付总金额/涉案歌曲数量）；
- **胜负判定**：结案原因 15 项（含重复「原告撤诉」），是唯一胜负信号；「律师代理费」字段类型错配（枚举复用结案原因前 5 项）；
- **关联**：涉及歌曲清单 DuplexLink ↔ 案号；父记录 SingleLink 自关联（系列案）；涉案歌曲-艺人是 Lookup 透传；
- **维度**：业务线 8 项、案由 12 项、案件状态 21 项、支付主体 3 项、收案年份（14 项混乱，需清洗）；
- **人员**：案件负责人（User）、撤卷申请人（User）、承办法官及联系方式（T，可解析）。

### 3.4 数据质量现状（清洗是 P0）

脏数据实测清单：收案年份混入公司名/数字/日期（14 选项）；原告选项混入案件状态与案号；被告选项含错别字公司名/简称/案由/空串；受理法院混入 3 家仲裁机构与截断文本；案号缺「号」字/带换行；结案原因重复项；律师代理费枚举错配。规则化清洗方案见 6.3 与 docs/03。

### 3.5 外部数据源可得性（调研结论摘要，详见 research/01）

- 裁判文书网：上网量 2020 年约 1920 万件 → 2023 年约 511 万件（-73%），2021 年后检索能力大幅削弱，**不可作为唯一网上判决支柱**；
- 替代候选：人民法院案例库（权威性最高）、北大法宝/威科先行/Alpha（商业 API）、把手案例等；选型结论见 research/01；
- 法律条文源：国家法律法规数据库（flk.npc.gov.cn）等。

## 5. UI/UX 原则

1. **数据密度优先**：法务查询场景使用紧凑表格+微图表，信息密度对标 BI 工具（Metabase/Grafana），而非营销页审美；
2. **暗色+亮色双主题**：默认亮色专业风，暗色为巡检/加班场景视觉降噪；主题切换即时生效，token 化设计（见 docs/02）；
3. **检索全站可达**：全局检索框吸顶常驻，`/` 快捷键聚焦，任何页面可发起检索；
4. **回答必带来源**：所有 AI 结论和统计数字需可下钻（点数字→明细抽屉）或带来源标注；
5. **原始与清洗并存**：脏数据以角标提示，可一键切换原始值/清洗值；
6. **状态可见**：同步状态条（上次同步时间/进行中进度/失败告警）全局可见；
7. **操作可审计**：导出、打标等关键操作记录。

## 6. 技术方案（v0.2 修正）

### 6.1 技术栈（与 v0.1 一致，理由不变）

| 层 | 选型 | 理由 |
|----|------|------|
| 前端 | React 18 + Vite + TypeScript + shadcn/ui + Tailwind CSS | 组件化快、暗/亮主题 token 化、图表库配套成熟 |
| 状态 | Zustand + TanStack Query | 服务端状态/缓存/重试开箱即用 |
| 表格 | TanStack Table（headless，虚拟滚动） | 64 万行实测方案，638 行起步无压力 |
| 图表 | ECharts（可选 Recharts 做轻量） | 下钻/联动/大屏型图表，中文化好 |
| 后端 | Python FastAPI + SQLAlchemy + SQLite（WAL） | 单机部署、同步/清洗管道用 Python 生态 |
| 检索 | SQLite FTS5（中文需分词方案选型，见 research/03） | 638~数万行本地检索 <300ms 无压力 |
| 任务调度 | APScheduler（内置定时）+ CLI 手动触发 | 天级同步 03:00，无需独立消息队列 |
| AI | Mode A：LLM API 抽象层（默认本地化配置，可切厂商）；Mode B：MCP 服务（FastMCP/官方 SDK） | 双模式共用检索内核 |
| 部署 | Docker Compose（前端 Nginx + 后端 + SQLite 卷）单机 | 目标本机/内网 10.10.11.37 类环境 |

### 6.2 数据同步引擎（v0.1 修正：补齐公式/关联/脏数据处理）

现状（v0.1 只有「天级同步+全量+单条」三句）→ 补足为完整设计（详见 docs/03）：

1. **同步对象**：案件表 35 字段 + 涉及歌曲清单表 + 父记录自关联 + User 字段人员解析；
2. **公式字段处理**：Formula（对方诉求支持率/单曲判赔/涉案歌曲数量）**不同步公式本身，同步计算结果值**（飞书 API 返回的 value），本地复刻公式仅为廉价重算（口径一致，docs/03 给出契约表）；
3. **Lookup/DuplexLink**：同步为关联 ID 映射，本地建 song_case 多对多表与 invitation 树（父记录）；
4. **清洗管道**：同步后立即跑清洗规则（规则表驱动），产出 derived 列，原始值保留（3.4）；
5. **增量策略**：记录级 offset 游标 + updated_at 筛选拉取；每日 03:00 增量、手动全量、单条刷新三级；
6. **写读分离**：写入 staging 表 → 校验 → 原子替换（SQLite 事务），查询永不被打断；
7. **失败重试**：3 次指数退避；同步日志（任务表/失败原因/重跑入口）持久化。

### 6.3 指标口径引擎（v0.1 新增：胜诉率落地）

- 胜诉率等 8 项指标操作化定义见需求文档 4.3；本地按「口径版本」存储（口径表可增改）；
- 任何图表/导出/AI 结论自动携带口径脚注；口径值变更只影响派生列，不动原始数据。

## 7. AI 智能体集成

### 7.1 Mode A（内置对话）

- 交互：全局检索栏右侧对话入口；「问数据」子模式：NL 意图解析 → 参数填充（年份/主体/案由/金额）→ 检索本地库 → 生成带来源回答；「问文书」子模式对接外部卷宗检索（远期）；
- 约束：回答强制附来源列表+口径脚注；置信度阈值低时提示人工核实；不产生幻觉数据（检索不到即说没有）；
- 模型接入：抽象层（$OPENAI_BASE/$MODEL 可配），默认兼容本地 Ollama/兼容端点，生产建议 64K 上下文模型。

### 7.2 Mode B（外挂 AI Agent · MCP）

- 暴露 8 类 MCP 工具：7 个报告模板 + 1 个「检索授权检查」（agent 调用前声明数据域）；
- 报告模板输入参数 JSON Schema 严格定义（见 8）；输出 Markdown/HTML 可存档；
- 只读：MCP 服务不暴露任何写操作；每次调用记审计。

## 8. MCP 报告模板（7 类，v0.1 保留并标准化）
